# Агент, LangGraph и офлайн-проверка

Актуальное подключение к единому main: [IGOR_INTEGRATION.md](IGOR_INTEGRATION.md).
`install_agent(app)` сохраняет приложение Игоря и добавляет insights/чат/trace
и персональную ленту. Хранение — в собственных `dima_agent_*` таблицах.
По умолчанию используется PostgreSQL FTS без embedding-модели; прежний hybrid
включается явно через `RAG_SEARCH_MODE=hybrid`. Лента не требует RAG;
при доступной LLM использует компактный профиль и пакетную оценку событий.
Запрос ленты не ждёт LLM: возвращаются кешированные оценки или предварительный локальный
подбор, а недостающие оценки рассчитываются в фоне общего `AgentRuntime`.
Зависимости MVP: [requirements-mvp.txt](requirements-mvp.txt).

Старая инструкция прототипа: [Integration_to_igor.md](../../../Integration_to_igor.md).
Готовый сервер: `uvicorn app.agent.api:create_app --factory` (PYTHONPATH=backend).
Рабочая логика больше не находится в `app.test`: `LLMClient` включает failover
и JSON-протокол, `service.answer_question` — деловой чат с предметной локальной помощью
при недоступной LLM/недостатке доказательств. Память восстанавливается из последних 12 обменов и необязательного состояния задачи;
передавайте history/turn_count из репозитория. Модель получает только три компактных обмена
и действующие условия пользователя. Явный сброс и смена темы очищают условия задачи.
Анализ сохраняет строгую проверку доказательств и 503 при недоступной LLM.

Полное объяснение архитектуры, потоков данных и интеграции с Игорем:
[EXPLANATION.md](../EXPLANATION.md).

`graph.py` реализует StateGraph с собственными узлами и ограниченными циклами;
`service.py` сохраняет публичные функции анализа и контекстного вопроса; `tools.py` — JSON- и сервисный
адаптеры; `recommendations.py` — объяснимый подбор новостей; `verifier.py` — проверки.
Обычная команда запуска ниже безопасна: используется `OfflineLLM`, без сети и ключей.
Живой клиент применяется только при явном подключении из backend.

## Профиль компании и релевантность

`relevance.py` отделяет исходные факты с путями полей от отраслевого описания LLM:
деятельности, зависимостей, чувствительных тем и предположений. Описание не становится
новыми фактами компании. Не отправляются исходный raw_profile, идентификатор компании
и платёжные связи. Один короткий запрос профиля ограничен 600 выходными токенами.

Лента выбирает до 24 кандидатов из локального подбора, совпадений с предметными
темами профиля и свежих новостей. Старый отраслевой фильтр больше не служит обязательным
условием отбора. Модель получает заголовок и до 1200 символов сохранённого краткого
описания новости (при его отсутствии — начало текста), оценивает до 8
новостей за вызов, максимум 3 пакета по 1800 выходных токенов. Это верхние лимиты,
а не гарантированный расход; входные токены и failover клиента оплачиваются отдельно.
Полный корпус новостей в LLM не отправляется. Выборка ограничена, поэтому полнота
отбора всех релевантных событий не гарантируется.

Профили и оценки кешируются в памяти одного `AgentRuntime` до 6 часов, с ограничением
размера и обновлением при изменении входных данных или модели. Недоступный профиль
кешируется на 60 секунд. Повторный запрос с теми же данными использует кеш.

Первое открытие ленты больше не ожидает до 55 секунд профиля и пакетных запросов:
на пути HTTP-ответа остаются загрузка данных и локальное ранжирование. Одна фоновая
задача на профиль заполняет кеш; максимум четыре профиля в очереди, генерация фоновых
лент последовательная. После завершения задачи действует пауза 30 секунд перед
новой попыткой при неполном результате. При остановке runtime задачи отменяются
до закрытия LLM-клиента. Отдельные вызовы с временными tools без общего runtime
возвращают локальный/кешированный подбор без запуска фоновой задачи.

Дополнительное поле `ranking_status`: `ready`, `refreshing` или `partial` показывает
полноту уточнения кандидатов. Текущий frontend не опрашивает этот статус:
уточнённый результат появляется при следующем запросе ленты. Автоматическое
обновление и отображение предварительного подбора требуют доработки на стороне Игоря.
Изменения frontend из этой доработки отменены. Холодный локальный подбор может
отличаться составом и порядком от последующего модельного результата.

Оценка содержит событие, адресатов, точную выдержку, механизм влияния, исходные поля
и неизвестные условия. Неизвестный срок принятия нормы или размер эффекта сам по себе
не исключает high: релевантность теме отделена от достоверности будущего последствия.
Неизвестная принадлежность компании к узкому кругу адресатов ограничивает high;
валютные новости без подтверждённой внешней торговли получают low. Общая новость
о ключевой ставке не получает high только по наличию банковского продукта.
Отсутствие связи исключает новость. Нет автоматического повышения за зарплатный проект.
При ошибке модели остаётся консервативный локальный подбор без high.

Для совместимости с текущим интерфейсом Игоря сохранены `relevance_score` и
`relevance_reasons`: high=80, medium=15, low=5. Интерфейс считает высокой оценку от 20.
Поля `relevance_level`, `relevance_method`, `event_analysis` сохраняются;
API передаёт явный уровень high/medium/low. Раздельные подписи и фильтры
требуют доработки на стороне Игоря.
Число служит порядковым баллом для совместимости, а не вероятностью влияния.

Подробный анализ получает ту же выжимку компании и краткое содержание новости.
Сохранённая оценка ленты используется в подробном анализе; новая оценка подробного
анализа попадает в общий кеш ленты. Перепланирование поиска не меняет уже проверенную
связь события с компанией. Невалидная цитата модели не кешируется как отсутствие связи.
Извлечение события и оценка связи объединены
с существующим запросом плана: отдельного вызова на эту оценку нет. Запрос профиля
учитывается в существующем лимите вызовов и токенов; при лимите менее трёх вызовов
используются только факты. Публичные DTO анализа и способы подключения сохранены.
После обновления версии промпта прежний кеш анализа не используется для новых запросов;
уже сохранённые результаты доступны по своим идентификаторам.

Ошибки схемы записываются с этапом, разрешёнными путями полей и типами ошибок,
без исходного ответа модели или значений. Основная генерация передаёт эти ошибки
в существующую единственную попытку исправления; бюджет вызовов не увеличен.
Повторный поиск не занимает последний вызов, необходимый для исправления анализа.
При ошибке JSON-схемы вспомогательного плана используется ограниченный поиск
по заголовку новости с предупреждением, без выдуманной оценки релевантности.
Ошибка основного анализа после доступного исправления по-прежнему не скрывается.

## Когда банковской аналитики не хватает

По ТЗ (с. 9, критерий 03; с. 11, ограничение 02; с. 12, ограничение 05;
с. 13, пространство решений) выводы AI отделяются от позиции банка, сервис работает
с неполными данными, а аналитика Альфа-Банка остаётся заметной частью продукта.
Прямого запрета на дополнительную AI-интерпретацию нет; полностью заменять ею
банковские материалы нельзя. Подключение чужой аналитики как замены материалам
Альфа-Банка этими положениями отдельно не разрешено.

Если подходящих материалов нет или позиция банка по событию не подтверждена,
агент продолжает анализ по готовой выжимке компании, краткому содержанию новости
и полученным доказательствам. Он объясняет условный механизм влияния, риски,
возможности и проверки. При установленной связи требуется хотя бы одно обоснованное
последствие со ссылкой на выбранную новость; оба направления искусственно не заполняются.
Если связи с бизнесом нет, последствия остаются пустыми.

В качественном режиме точные числа запрещены в персональных последствиях,
объяснении и действиях. Числа исходной новости сохраняются в дословных фактах;
датированные точные цитаты банка допустимы как исторический фон. Позиция банка
остаётся `not_found`; предупреждения ответа явно отмечают AI-происхождение оценки и отсутствие
точного расчёта. Поиск банка и проверка источников сохраняются. Новый внешний
источник аналитики не подключается. Версия промпта обновлена для сброса старого кеша.

## LLM-клиент

- `config.py`: настройки на `pydantic-settings`, проверка URL и выбор модели.
- `models.json`: соответствие коротких alias точным API ID моделей.
- `llm_client.py`: асинхронный `LLMClient`.
- `schema.py`: Pydantic-схемы запросов, анализа, источников, trace, чата
  и ответов LLM (`LLMReply`, `TokenUsage`).

`AgentAnalysis` содержит `result` и `agent_trace` до сохранения;
`InsightResponse` добавляет идентификаторы и статус для API.
Схемы проверяют уникальность источников и ссылки на них. Позиция банка
`found` требует текста и ссылки на банковский документ с номером страницы.
Verifier должен отдельно проверять содержание доказательств, пути
`company_fields` и ссылки ответа чата по сохранённому контексту.

Установить зависимости из `backend/requirements.txt` в окружение проекта.
Настройки читаются из `.env` в корне `alfa-insight`, независимо от текущей
директории. Переменные окружения имеют приоритет над `.env`.

| Переменная | Назначение |
| --- | --- |
| `LLM_BASE_URL` | HTTPS URL API организаторов, включая `/v1` |
| `LLM_API_KEY` | Ключ; хранить только в локальном `.env` или окружении |
| `LLM_MODEL` | Alias из `models.json` или точный ID из значений этого файла |
| `LLM_TIMEOUT_SECONDS` | Таймаут запроса, по умолчанию 30 секунд |
| `LLM_MAX_TOKENS` | Лимит выходных токенов, по умолчанию 256 |

`LLMSettings` валидирует настройки через Pydantic, ключ хранится как `SecretStr`.
Два URL проверялись с моделью `deepseek-v4.1`; доступность может меняться.
Настройки также включают `LLM_FALLBACK_BASE_URL`, `LLM_REASONING_EFFORT=none`
и `LLM_JSON_MODE=true`. Метрики доступны в `LLMClient.diagnostics`, без промптов.

Пример использования настоящего клиента внутри async-функции (выполнение расходует
лимит, в текущей работе не запускался):

```python
from app.agent.llm_client import LLMClient

async with LLMClient() as client:
    reply = await client.generate_text("Ответь одним словом: OK")
    print(reply.text)
```

Для диалога с историей или системной инструкцией используется
`await client.complete(messages)`. Оба метода принимают `model="kimi-k2.6"`
для смены модели на один вызов. Настройки можно передать явно через
`LLMClient(settings=LLMSettings(...))`.

В FastAPI клиент следует создать один раз на время lifespan приложения
и закрыть через `await client.aclose()` при завершении. Это позволяет
переиспользовать соединения и не блокировать event loop ожиданием LLM.

Ответ `LLMReply` содержит текст, модель, `TokenUsage`, время и причину завершения.
`finish_reason=length` означает достижение лимита выходных токенов.
Ошибки провайдера преобразуются в `LLMError` без тела ответа и ключа;
для HTTP-ошибок доступен `status_code`. Ошибки настроек — `LLMConfigurationError`,
пустые аргументы запроса — `ValueError`.

## Офлайн-отладка без токенов

`main()` использует только учебные JSON и офлайн-заглушку модели. Запуск из корня проекта:

```bash
PYTHONPATH=backend .venv/bin/python -m app.agent.main
```

Команда не создаёт LLMClient и не загружает `.env`. Риски и возможности в таком
примере остаются пустыми: реальный анализ моделью не имитируется.

```bash
PYTHONPATH=backend .venv/bin/python -m unittest discover -s backend/app/agent/tests -v
PYTHONPATH=backend .venv/bin/python -m app.rag.evaluate
```

В настоящем агенте ограничены количество LLM-вызовов, уточнение поиска и исправление
ответа. Сам SDK автоматических повторов не делает. Публичные DTO сохранены.

## Политика предметной помощи

[Отчёт и ограничения проверки](OPPORTUNITIES_REPORT.md). Смысл признаков переводится
в человеческий язык до генерации; готовая проза проверяется отдельно от метаданных.
Одно исправление формулировки входит в прежний бюджет. Неизвестные флаги не получают
выдуманных объяснений. Старые сохранённые анализы остаются исходными снимками.

Чат использует числа пользователя с явной атрибуцией и локальные Decimal-расчёты.
Сохраняемое состояние не содержит догадок из ответов модели. Собственный репозиторий
атомарно сохраняет сообщение и необязательную область контекста; минимальный сторонний
репозиторий продолжает работать с доступной ему историей. Новых обязательных методов нет.

Дополнительный локальный поиск использует только уже созданное хранилище. Новые
материалы допускаются при возможности надёжного сохранения, с названием, датой и
страницей в самом ответе; список источников исходного анализа остаётся неизменным.
Поиск не создаёт индекс при простом вопросе и не обращается в Интернет.

Проверка размеченной матрицы без модели и базы:

```bash
PYTHONPATH=backend .venv/bin/python -m app.agent.evaluate_relevance
```
